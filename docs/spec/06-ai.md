# 06 — Combat AI

Read `docs/spec/00-architecture.md` and `docs/spec/contracts/core.ts` in full before this document; where anything here appears to disagree with either, they win. This module implements `contracts/ai.ts` (module 06's own contract) inside `src/ai/`.

## 1. Purpose & scope

`src/ai` implements `core.ts`'s `Pilot` interface for every non-player aircraft. An `AiPilot` receives exactly the same `PilotContext` the human player's `PlayerPilot` (src/input) would receive for that aircraft — `self`/`telemetry` (its own state), `contacts` (sensor tracks, never ground truth), `combat` (its own weapon/lock status), `sampler` (terrain), `navDb` (airports), `windWorldMps`, `simTimeSec` — and returns `PilotInputs` through the identical `Pilot.update(ctx, dtSec, out)` call the sim worker makes for every Pilot-bearing aircraft every `SIM_DT_SEC`. **The AI is not given, and must never read, another entity's true `EntityState`, `DamageState` or `AircraftDefinition`.** Every decision below is derived only from `PilotContext`'s fields, which is what makes "no cheating" true by construction rather than by convention.

The module is a **two-layer controller**:

1. **Tactical layer** (`tacticalFsm.ts` + `bfmManoeuvres.ts` + `threatEvaluation.ts` + `weaponEmployment.ts` + `formation.ts` + `landing.ts`) — a discrete decision layer, re-evaluated every tick but changing state only occasionally (section 4.7's dwell-time rule), that decides *what* the aircraft should be doing right now and expresses it as one `FlightGoal` (contracts/ai.ts): a desired bank angle, a desired g-load-or-altitude, a desired speed, and gear/airbrake/throttle-override flags.
2. **Control layer** (`steering.ts`) — a continuous PD/PI layer, run every tick unconditionally, that turns whatever `FlightGoal` the tactical layer last produced into `PilotInputs` via the exact same kind of stick/rudder/throttle commands a human would give, which then pass through `src/physics`'s FCS (module 02) exactly as the player's inputs do. The AI never touches a control surface deflection, force or moment directly.

A terrain-avoidance safety check (`terrainAvoidance.ts`) runs after the tactical layer and can override its `FlightGoal` for the tick; nothing else in the pipeline can veto it.

Out of scope for this module: actually firing weapons (bullet/missile spawning, ballistics, guidance, hit resolution — all `src/combat`, module 07), actually deflecting control surfaces or integrating the rigid body (`src/physics`, module 02), rendering anything (`src/render`/`src/hud`). This module only ever produces a `PilotInputs` value (plus, via its `AiPilotDebugState`, a read-only record of *why*).

## 4. Design & algorithms

### 4.1 Per-tick orchestration (`pilotAi.ts`)

```ts
class AiPilotImpl implements AiPilot {
  // constructed once in createAiPilot(params); all fields below are reused,
  // never reallocated, across update() calls.
  private state: TacticalState = TacticalState.Patrol;
  private timeInStateSec = 0;
  private manoeuvre: BfmManoeuvre | undefined;
  private timeInManoeuvreSec = 0;
  private targetId: EntityId | undefined;
  private targetScore = 0;
  private goal: FlightGoal = { /* pooled, fully populated at construction */ };
  private terrainGoal: FlightGoal = { /* pooled scratch, owned by terrainAvoidance.ts */ };
  private firstSeenSimTimeSec = new Float64Array(MAX_ENTITIES).fill(-1); // indexed by unpackEntityId(id).index — reaction-delay memory, section 4.13
  private missileWarningFirstSeenSimTimeSec = -1;
  private missileWarningNoticedAt = -1;
  private rng: Mulberry32State; // seeded from params.seed, src/math
  private lastLaunchSimTimeSec = -1e9;
  private speedIntegral = 0;
  public readonly debug: AiPilotDebugState = { /* mirrors the fields above every tick, see below */ };

  update(ctx: PilotContext, dtSec: number, out: PilotInputs): void {
    this.timeInStateSec += dtSec;
    this.timeInManoeuvreSec += dtSec;

    const missileWarningNoticed = this.updateMissileWarningNotice(ctx, dtSec); // 4.13
    const perceivedContacts = this.filterPerceived(ctx, dtSec);               // 4.13, reuses a pooled array

    const next = evaluateTacticalTransition(
      ctx, this.state, this.timeInStateSec, AiDifficultyProfiles[this.difficulty],
      this.formationLeaderAlive(ctx), missileWarningNoticed);
    if (next !== this.state) {
      this.state = next; this.timeInStateSec = 0; this.manoeuvre = undefined; this.timeInManoeuvreSec = 0;
    }

    const target = selectTarget(ctx, perceivedContacts, this.targetId, AiDifficultyProfiles[this.difficulty]); // 4.5
    this.targetId = target?.id; this.targetScore = target ? scoreThreatContact(ctx, target) : 0;

    this.buildGoalForState(ctx, target, dtSec); // 4.8/4.10/4.11/4.12/4.12a/4.12b/4.12c, writes this.goal

    const override = computeTerrainAvoidanceGoal(ctx, this.goal, dtSec); // 4.4, highest priority
    const activeGoal = override ?? this.goal;

    steerToGoal(ctx, activeGoal, dtSec, out); // 4.2-4.3, fills pitch/roll/yaw/throttle/afterburner/brakes/gearDown/airbrake

    this.decideWeaponEmployment(ctx, target, dtSec, out); // 4.9, fills trigger/launch/cycleWeapon/cycleTarget

    this.syncDebugState();
  }
}
```

`out.nwsEnabled` is left `undefined` (treated as `false` per core.ts) — the AI never uses nose-wheel steering; ground taxiing after landing uses differential nothing (rudder + brakes only), acceptable for this project's scope (see section 9).

### 4.2 Control layer — attitude loops (`steerToGoal`)

Inputs available every call: `ctx.self.omega` (body rates), `ctx.telemetry` (`rollRad`, `pitchRad`, `alphaRad`, `betaRad`, `gLoad`, `iasMps`, `stalled`), `goal` (`FlightGoal`). Body-rate accessors per 00-architecture.md 3.4: `p = omega.x`, `q = omega.z`, `r = -omega.y` (only `p` and `q` are needed here).

**Bank (roll):**
```
bankErrorRad = wrapPi(goal.desiredBankRad - telemetry.rollRad)
out.roll = clamp(ControlGains.BANK_KP * bankErrorRad - ControlGains.BANK_RATE_KD * omega.x, -1, 1)
```
Worked example: `bankErrorRad = 0.349066` (20°), `omega.x = 0` → `out.roll = 2.2 * 0.349066 = 0.767945`.

**Pitch — g_load mode** (`goal.pitchMode === 'g_load'`): first clamp for stall protection —
```
effectiveG = telemetry.stalled ? Math.min(goal.desiredGLoad, 1.0) : goal.desiredGLoad
gErrorG = effectiveG - telemetry.gLoad
out.pitch = clamp(ControlGains.G_KP * gErrorG - ControlGains.G_RATE_KD * omega.z, -1, 1)
```
Worked example: `effectiveG = 4`, `telemetry.gLoad = 1`, `omega.z = 0` → `out.pitch = 0.12 * 3 = 0.36`.

**Pitch — altitude_hold mode** (`goal.pitchMode === 'altitude_hold'`):
```
altErrorM = goal.desiredAltitudeM - telemetry.altMslM
targetFpaRad = clamp(ControlGains.ALT_TO_FPA_KP * altErrorM, -ControlGains.MAX_ALT_HOLD_FPA_RAD, ControlGains.MAX_ALT_HOLD_FPA_RAD)
currentFpaRad = telemetry.pitchRad - telemetry.alphaRad          // gamma = theta - alpha, wings-level approximation (see section 9)
fpaErrorRad = targetFpaRad - currentFpaRad
out.pitch = clamp(ControlGains.FPA_KP * fpaErrorRad - ControlGains.FPA_RATE_KD * omega.z, -1, 1)
```
Worked example: `altErrorM = 500` → `raw = 0.006*500 = 3.0`, clamped to `0.174533`; `pitchRad = 0`, `alphaRad = 0.05` → `currentFpaRad = -0.05`; `fpaErrorRad = 0.224533`; `omega.z = 0` → `out.pitch = 2.0 * 0.224533 = 0.449066`.

**Yaw (sideslip coordination):** `betaRad > 0` means the relative wind arrives from the right, i.e. the nose is yawed left of the true velocity vector; commanding "nose right" (`PilotInputs.yaw = +1` per core.ts) rotates the nose toward the velocity vector and reduces `betaRad`, so the gain is positive:
```
out.yaw = clamp(ControlGains.YAW_BETA_KP * telemetry.betaRad, -1, 1)
```
Worked example: `betaRad = 0.1` → `out.yaw = 1.4 * 0.1 = 0.14`.

**Gear/airbrake:** `out.gearDown = goal.gearDown; out.airbrake = goal.airbrake; out.brakes = ctx.self.flags & EntityFlag.OnGround ? (goal.desiredSpeedMps < 5 ? 1 : 0) : 0` — full wheel braking only when on the ground and trying to stop (landing rollout / RTB taxi), never in the air.

### 4.3 Control layer — speed hold & throttle

```
if (goal.throttleOverride !== undefined) {
  out.throttle = clamp(goal.throttleOverride, 0, 1);
  this.speedIntegral = 0;                                    // avoid windup while overridden
} else {
  const speedErrorMps = goal.desiredSpeedMps - telemetry.iasMps;
  this.speedIntegral += speedErrorMps * dtSec;
  const iTerm = clamp(ControlGains.SPEED_KI * this.speedIntegral,
                       -ControlGains.SPEED_INTEGRAL_CLAMP, ControlGains.SPEED_INTEGRAL_CLAMP);
  out.throttle = clamp(ControlGains.SPEED_THROTTLE_BIAS + ControlGains.SPEED_KP * speedErrorMps + iTerm, 0, 1);
}
out.afterburner = goal.afterburnerOverride === true
  || (out.throttle >= 0.999 && (goal.desiredSpeedMps - telemetry.iasMps) > ControlGains.AB_ENGAGE_SPEED_DEFICIT_MPS);
```
Worked example (no override, `speedIntegral = 0` at tick start): `desiredSpeedMps = 250`, `iasMps = 230` → `speedErrorMps = 20` → `out.throttle = clamp(0.5 + 0.008*20 + 0, 0, 1) = 0.66`.

### 4.4 Terrain avoidance (`terrainAvoidance.ts`)

Runs every tick, after the tactical layer, before steering. Projects the ground track forward using current `ctx.self.vel` (world-frame, horizontal component) for `TerrainAvoidanceParams.LOOKAHEAD_SEC` seconds. The sample COUNT is distance-adaptive, not fixed at `SAMPLE_COUNT` (5): a fixed 5-point scheme spaces samples `LOOKAHEAD_SEC * |vel_horizontal| / 4` apart, which at a representative low-level BFM/terrain-hugging speed of 220–280 m/s is ~330–420 m between samples — wide enough that a ridge narrower than the gap, with both flanking samples individually clear, is never detected even though the flight path actually crosses it. `SAMPLE_SPACING_MAX_M` (100 m) bounds this:

```
speedHorizontal = hypot(self.vel.x, self.vel.z)
sampleCount = clamp(
  ceil(speedHorizontal * TerrainAvoidanceParams.LOOKAHEAD_SEC / TerrainAvoidanceParams.SAMPLE_SPACING_MAX_M) + 1,
  TerrainAvoidanceParams.SAMPLE_COUNT,        // never fewer than 5, even standing still
  TerrainAvoidanceParams.SAMPLE_COUNT_MAX)    // never more than 40 — worst-case heightAt-call budget, see section 6

for i in 0..sampleCount-1:
  t = i / (sampleCount - 1) * LOOKAHEAD_SEC
  sampleX = self.pos.x + self.vel.x * t
  sampleZ = self.pos.z + self.vel.z * t
  projectedY = self.pos.y + self.vel.y * t
  terrainY = ctx.sampler.heightAt(sampleX, sampleZ)
  clearanceM = projectedY - terrainY
  if clearanceM < worstClearanceM: worstClearanceM = clearanceM; worstIndex = i
```

Worked example: at `speedHorizontal = 250 m/s`, `sampleCount = clamp(ceil(250*6/100)+1, 5, 40) = clamp(16, 5, 40) = 16` samples, spaced exactly `100 m` apart — versus the fixed scheme's 5 samples at ~375 m apart. At low patrol speed (`speedHorizontal = 60 m/s`), `sampleCount = clamp(ceil(60*6/100)+1, 5, 40) = clamp(5, 5, 40) = 5`, i.e. the original fixed count, since spacing is already well under 100 m. Per-aircraft worst case (40 samples) across up to 8 simultaneous AI aircraft (section 6's own concurrency assumption) is 320 `heightAt` calls/tick — still the dominant per-tick AI cost, budgeted explicitly in section 6.
- If `worstClearanceM >= TerrainAvoidanceParams.MIN_CLEARANCE_M` (150 m): return `undefined` (no override).
- Else: build and return an override `FlightGoal` (into the pooled `terrainGoal` object): `pitchMode = 'g_load'`, `desiredBankRad = 0` (wings-level pull, the fastest way to gain altitude), `desiredGLoad = worstClearanceM < TerrainAvoidanceParams.HARD_MIN_CLEARANCE_M ? difficulty.maxCommandedGLoad : difficulty.maxCommandedGLoad * 0.7` (full commanded-g ceiling only once below the hard emergency threshold; a softer 70% pull between `HARD_MIN_CLEARANCE_M` and `MIN_CLEARANCE_M`), `desiredSpeedMps = telemetry.iasMps` (do not also demand a speed change while pulling up), `throttleOverride = 1.0`, `afterburnerOverride = worstClearanceM < TerrainAvoidanceParams.HARD_MIN_CLEARANCE_M`, `gearDown = false`, `airbrake = false`.

This override is unconditional — it fires regardless of `TacticalState`, including `Land` (a real GPWS would too; `Land`'s own logic, section 4.11, keeps the aircraft well above `MIN_CLEARANCE_M` relative to the runway's flattened terrain in normal operation, so this only fires for a genuinely bad approach or a hostile terrain-masking manoeuvre).

### 4.5 Threat evaluation & target selection (`threatEvaluation.ts`)

A contact is a **candidate** only if `contact.identified && contact.team !== ctx.self.team && contact.rangeM <= difficulty.saRadiusM` — this is the module's one Rules-Of-Engagement check, directly enforcing core.ts's `Contact.identified` comment ("must not read `.team` on an unidentified contact as ground truth for weapons-free decisions"): an unidentified contact is never scored, targeted or fired upon, only ever a reason to stay in `Intercept` and close range for a visual ID.

```
aspectAngleRad = computeAspectAngleRad(headingFromVelocity(contact.vel), contact.pos, self.pos)
threatFromAspect = 1 - Math.abs(aspectAngleRad) / Math.PI            // 1 = contact pointed at self, 0 = self on contact's tail
rangeTerm   = ThreatWeights.W_RANGE   * (1 - clamp(contact.rangeM / difficulty.saRadiusM, 0, 1))
closureTerm = ThreatWeights.W_CLOSURE * clamp(contact.closureMps / ThreatWeights.CLOSURE_NORM_MPS, -1, 1)
aspectTerm  = ThreatWeights.W_ASPECT  * threatFromAspect
altTerm     = ThreatWeights.W_ALT     * clamp((contact.pos.y - self.pos.y) / ThreatWeights.ALT_NORM_M, -1, 1)
score = rangeTerm + closureTerm + aspectTerm + altTerm
```
Worked example: `rangeM = 5000`, `saRadiusM = 14000` → `rangeTerm = 3*(1-0.357143) = 1.928571`; `closureMps = 100` → `closureTerm = 2*0.5 = 1.0`; head-on (`aspectAngleRad = 0`) → `aspectTerm = 4*1 = 4`; `contact.pos.y - self.pos.y = 1500` → `altTerm = 1*0.5 = 0.5`; `score = 1.928571+1.0+4+0.5 = 7.428571`.

**`selectTarget`**: score every candidate; let `best` be the highest-scoring one. If there is no currently-locked `targetId`, or the current target is no longer a candidate (dead/out of range/lost ID), pick `best`. Otherwise keep the current target unless `score(best) - score(currentTarget) > ThreatWeights.TARGET_SWITCH_HYSTERESIS` (1.5), preventing single-tick target flicker between two similarly-scored contacts. Returns `undefined` when there are no candidates (drives `Patrol`/`Rtb`).

### 4.6 Energy state (`energyState.ts`)

Standard energy-height formula, dimensioned as metres:
```
computeEnergyHeightM(altitudeM, trueAirspeedMps) = altitudeM + (trueAirspeedMps * trueAirspeedMps) / (2 * GRAVITY_MPS2)
```
Worked example: `altitudeM = 3000`, `trueAirspeedMps = 200` → `3000 + 40000 / 19.6133 = 3000 + 2039.7877 = 5039.7877` m.

`selfEnergyHeightM = computeEnergyHeightM(telemetry.altMslM, telemetry.tasMps)`. A contact's true airspeed is not observable, so `targetEnergyHeightM = computeEnergyHeightM(contact.pos.y, |contact.vel|)` uses ground speed as a true-airspeed proxy (acceptable: wind speeds are small relative to fighter airspeeds, and this value only feeds BFM manoeuvre *selection*, never a physics calculation). `energyDeficitM = targetEnergyHeightM - selfEnergyHeightM` (positive = target has more energy than self).

### 4.7 Tactical FSM (`tacticalFsm.ts`)

`evaluateTacticalTransition` evaluates the rules below **in this exact priority order** every tick and returns the first matching state; if none match, it returns `current` unchanged. Rules 1-3 and the `Land`-abort rule (10) ignore `BfmThresholds.MIN_STATE_DWELL_SEC`; every other transition additionally requires `timeInStateSec >= BfmThresholds.MIN_STATE_DWELL_SEC` (1.5 s) before it is allowed to fire, or it is skipped this tick (return `current`).

| # | condition | → state |
|---|---|---|
| 1 | `missileWarningNoticed === true` | `Defensive` |
| 2 | current is not already `Disengage`\|`Rtb`\|`Land` (i.e. any of `Patrol`\|`Intercept`\|`Bfm`\|`Defensive`\|`Merge`\|`EngageBvr`) and (`telemetry.fuelFrac < BfmThresholds.DISENGAGE_FUEL_FRAC` or (`combat.ammoGun===0 && combat.missilesIr===0 && combat.missilesRadar===0`)) | `Disengage` |
| 3 | current is `Land` and nearest identified-hostile candidate range `< BfmThresholds.LAND_ABORT_THREAT_RANGE_M` | `Defensive` |
| 4 | current is `Disengage` and (no identified-hostile candidate within `BfmThresholds.DISENGAGE_SAFE_RANGE_M`, or none at all) | `Rtb` |
| 5 | current is `Rtb` and `resolveHomeRunway(ctx, homeAirportId, homeRunwayId)` (section 4.11) returns a defined `RunwayInfo` and range to its threshold `<` that runway's `ils` capture range (a fixed `LOCALISER_CAPTURE_RANGE_M`, section 4.11) | `Land` |
| 6 | current is `Land` | `Land` (no further checks besides rule 3; `Land`'s own goal builder, 4.11, transitions the AI to a terminal taxi/park behaviour once `EntityFlag.OnGround` is set, outside the FSM) |
| 7 | no identified-hostile candidate exists (section 4.5) | `Patrol` (wingmen report `Patrol` too; `buildGoalForState` special-cases a wingman's `Patrol` goal to follow its leader instead of a patrol anchor, section 4.10) |
| 8 | best candidate `rangeM <= AiWeaponEnvelope.RADAR_MAX_RANGE_M` and `combat.lockState === AiWeaponEnvelope.RADAR_REQUIRED_LOCK` and `combat.missilesRadar > 0` | `EngageBvr` |
| 9 | best candidate `rangeM > BfmThresholds.ENGAGE_BVR_MIN_RANGE_M` (5000 m) | `Intercept` |
| 10 | best candidate `rangeM > BfmThresholds.VISUAL_MANOEUVRE_RANGE_M` (1800 m) | `Merge` |
| 11 | best candidate `aspectAngleRad` (from the target toward self, section 4.5) has `threatFromAspect >= 0.5` (target has decent nose-on aspect on self) | `Defensive` |
| 12 | otherwise | `Bfm` |

Rules 8 and 9 are ordered deliberately: rule 8 (`EngageBvr`) is checked *before* rule 9 (`Intercept`) so that a radar-locked AI with radar missiles ready fires them as soon as the target is inside `RADAR_MAX_RANGE_M` (18000 m), rather than always falling through to `Intercept` for any `rangeM > ENGAGE_BVR_MIN_RANGE_M`. Because rule 8 is checked first, rule 9 is in practice only reached once the AI is beyond BVR-engage range (5000 m) but does *not yet* have a valid radar lock/missile — i.e. `Intercept` means "close the range or resolve tracking before a BVR shot is possible," which is the intended behaviour: `Intercept`'s goal (section 4.12) closes range and points the nose at the target so `combat`'s radar/lock logic (module 07) gets a chance to achieve `RADAR_REQUIRED_LOCK`.

`formationLeaderAlive` (passed in) only affects `buildGoalForState`'s formation-following branch (section 4.10), not this table.

### 4.8 BFM manoeuvre library (`bfmManoeuvres.ts`)

`selectBfmManoeuvre` is called only from `TacticalState.Bfm` (offensive set) or `TacticalState.Defensive` (defensive set); it never mixes the two sets. Only the SELECTION/GATING thresholds below (`HIGH_YOYO_MIN_ANGLE_OFF_DEG`, `HIGH_YOYO_MAX_RANGE_M`, `LOW_YOYO_MAX_ANGLE_OFF_DEG`, `LOW_YOYO_MIN_ENERGY_DEFICIT_M`, `LOW_YOYO_MAX_RANGE_M`, `LAG_PURSUIT_MAX_RANGE_M`, `LEAD_PURSUIT_MIN_ANGLE_OFF_DEG`, `BREAK_TURN_TRIGGER_RANGE_M`, `BREAK_TURN_TRIGGER_ANGLE_OFF_DEG`, `EXTENSION_MIN_ENERGY_ADVANTAGE_M`, `JINK_TRIGGER_RANGE_M`) are first multiplied by `difficulty.bfmSkillMultiplier`; every goal-construction PARAMETER (`BASE_PURSUIT_G_LOAD`, `PURSUIT_ELEVATION_G_GAIN`, `HIGH_YOYO_BANK_SCALE`, the `*_OFFSET_RAD` pair, `BREAK_TURN_THROTTLE`, `NOTCH_G_LOAD`, `JINK_PERIOD_SEC`, `JINK_MAX_BANK_RAD`, `DISENGAGE_BANK_RAD`) is used raw — see `contracts/ai.ts`'s `BfmThresholds` header comment for the authoritative, exhaustive list (an earlier drafting pass here said "every threshold," which was wrong for the goal-construction parameters and is now corrected).

**Hysteresis (prevents tick-to-tick oscillation).** `selectBfmManoeuvre` only returns a value different from `previous` when `timeInManoeuvreSec >= BfmThresholds.BFM_MANOEUVRE_MIN_DWELL_SEC` (1.0 s), EXCEPT a `Notch` triggered by a fresh `missileWarningNoticed` (defensive rule 1), which fires immediately — mirroring the FSM's own `MIN_STATE_DWELL_SEC` exemption for safety-critical transitions (section 4.7). Otherwise it returns `previous` unchanged, even if a different rule would now match. This matters because every selection rule above is a memoryless per-tick threshold comparison (e.g. rule 1's `target.rangeM < HIGH_YOYO_MAX_RANGE_M` vs. the `LeadPursuit` fallback) re-evaluated at 120 Hz; without this dwell, a target's range or angle-off oscillating by a few metres/degrees around a boundary — entirely plausible during real manoeuvring — would otherwise flip `desiredBankRad`/`desiredGLoad` between two very different values every tick. `pilotAi.ts` calls `selectBfmManoeuvre` once per tick and compares the result against `this.manoeuvre`: on a change it sets `this.manoeuvre = result` and resets `this.timeInManoeuvreSec = 0` (in addition to the reset already performed on a `TacticalState` change, section 4.1) *before* calling `buildBfmGoal`, so `Jink`'s `JINK_PERIOD_SEC` redraw cadence (below) always starts counting from the moment `Jink` was actually selected, not from whenever the enclosing state was entered.

**Offensive (`Bfm`), evaluated in order, `angleOffRad = |target.bearingRad|`:**

1. `angleOffRad > HIGH_YOYO_MIN_ANGLE_OFF_DEG°` and `target.rangeM < HIGH_YOYO_MAX_RANGE_M` and `target.closureMps > 0` → `HighYoYo`.
2. `angleOffRad <= LOW_YOYO_MAX_ANGLE_OFF_DEG°` and `energyDeficitM >= LOW_YOYO_MIN_ENERGY_DEFICIT_M` and `target.rangeM <= LOW_YOYO_MAX_RANGE_M` → `LowYoYo`.
3. `target.rangeM < LAG_PURSUIT_MAX_RANGE_M` → `LagPursuit`.
4. `angleOffRad > LEAD_PURSUIT_MIN_ANGLE_OFF_DEG°` → `LeadPursuit`.
5. otherwise → `PurePursuit`.

**Defensive (`Defensive`), evaluated in order:**

1. `missileWarningNoticed` (passed through `ctx.combat.missileInboundWarning`, already gated at the FSM level to have entered `Defensive`) → `Notch`.
2. `target.rangeM <= BREAK_TURN_TRIGGER_RANGE_M` and `threatFromAspect` (of the attacker on self) corresponds to `|aspectAngleRad| <= BREAK_TURN_TRIGGER_ANGLE_OFF_DEG°` → `BreakTurn`.
3. `(selfEnergyHeightM - targetEnergyHeightM) > EXTENSION_MIN_ENERGY_ADVANTAGE_M` and `target.rangeM > BREAK_TURN_TRIGGER_RANGE_M` → `Extension`.
4. `target.rangeM <= JINK_TRIGGER_RANGE_M` → `Jink`.
5. otherwise → `BreakTurn` (safe default).

**`buildBfmGoal`** — per-manoeuvre `FlightGoal` construction, all use `pitchMode = 'g_load'` and `gearDown = false, airbrake = false` unless noted:

- **PurePursuit**: `desiredBankRad = clamp(ControlGains.HEADING_TO_BANK_KP * target.bearingRad, -ControlGains.MAX_MANOEUVRE_BANK_RAD, ControlGains.MAX_MANOEUVRE_BANK_RAD)`; `desiredGLoad = clamp(BASE_PURSUIT_G_LOAD + PURSUIT_ELEVATION_G_GAIN * clamp(target.elevationRad, -0.5, 0.5), Math.max(1, difficulty.minCommandedGLoad), difficulty.maxCommandedGLoad)`; `desiredSpeedMps = telemetry.iasMps` (hold current speed, let g-loop do the work); no override.
- **LeadPursuit**: same as PurePursuit but `leadBearingRad = target.bearingRad + Math.sign(target.bearingRad || 1) * LEAD_PURSUIT_OFFSET_RAD` feeds the bank formula in place of `target.bearingRad`.
- **LagPursuit**: same as PurePursuit but `lagBearingRad = target.bearingRad - Math.sign(target.bearingRad || 1) * LAG_PURSUIT_OFFSET_RAD` feeds the bank formula; `desiredGLoad` capped at `BASE_PURSUIT_G_LOAD` (no elevation bonus — deliberately wide/gentle to avoid overshoot).
- **HighYoYo**: `desiredBankRad = HIGH_YOYO_BANK_SCALE * (ControlGains.HEADING_TO_BANK_KP * target.bearingRad)`; `desiredGLoad = BASE_PURSUIT_G_LOAD * 0.6` (partial unload — this reduced bank + reduced g combination is what climbs the nose above the turn circle, section 4.8 rationale below).
- **LowYoYo**: `desiredBankRad = clamp(ControlGains.HEADING_TO_BANK_KP * target.bearingRad, -ControlGains.MAX_MANOEUVRE_BANK_RAD, ControlGains.MAX_MANOEUVRE_BANK_RAD)` (full pursuit bank); `desiredGLoad = difficulty.maxCommandedGLoad` (commit to max sustained turn performance, trading altitude for rate via the flight model's own energy dynamics).
- **BreakTurn**: `desiredBankRad = Math.sign(target.bearingRad || 1) * ControlGains.MAX_MANOEUVRE_BANK_RAD`; `desiredGLoad = difficulty.maxCommandedGLoad`; `throttleOverride = BfmThresholds.BREAK_TURN_THROTTLE` (0.7).
- **Notch**: `desiredBankRad = clamp(Math.sign(target.bearingRad || 1) * ControlGains.HEADING_TO_BANK_KP * (Math.abs(target.bearingRad) - BfmThresholds.NOTCH_BEAM_OFFSET_RAD), -ControlGains.MAX_MANOEUVRE_BANK_RAD, ControlGains.MAX_MANOEUVRE_BANK_RAD)`. This single expression turns the aircraft toward whichever direction moves the threat's bearing toward the ±90° beam: when `|bearingRad| < 90°` (threat ahead of the beam) the product's sign is the *opposite* of `sign(bearingRad)`, i.e. turn away from the threat; when `|bearingRad| > 90°` (threat aft of the beam) the sign matches `sign(bearingRad)`, i.e. turn toward it, pulling it forward to the beam instead of letting it go further aft. `desiredGLoad = BfmThresholds.NOTCH_G_LOAD` (2.5).
- **Extension**: `desiredBankRad = 0`; `desiredGLoad = 1.0`; `throttleOverride = 1.0`; `afterburnerOverride = true`; `desiredSpeedMps = telemetry.iasMps` (irrelevant, overridden).
- **Jink**: every `BfmThresholds.JINK_PERIOD_SEC` (0.6 s, tracked via `timeInManoeuvreSec` modulo), redraw `desiredBankRad` uniformly from `[-JINK_MAX_BANK_RAD, JINK_MAX_BANK_RAD]` and `desiredGLoad` uniformly from `[difficulty.minCommandedGLoad, difficulty.maxCommandedGLoad]` using this `AiPilot`'s own `mulberry32` stream (never `Math.random`), holding both fixed between redraws; `throttleOverride = 1.0`.

*High/Low Yo-Yo rationale*: this module does not model a true out-of-plane 3-D pursuit geometry (see section 9); High-Yo-Yo's *reduced* bank+g combination leaves more of the aircraft's lift vector pointed upward than a full pursuit turn would, so the flight model's own vertical dynamics carry the nose above the turn circle while angle-off bleeds off — a deliberately simplified but physically-motivated stand-in for the manoeuvre's real geometry. Low-Yo-Yo's *maximum* bank+g commits to the tightest sustained turn the AI is willing to fly, which necessarily bleeds altitude for turn rate under this project's flight model, the low-yo-yo's real-world effect.

### 4.9 Weapon employment (`weaponEmployment.ts`)

`estimateWeaponEnvelope(ctx, weapon, target)`:
```
switch weapon:
  case 'gun':
    timeOfFlightSec = target.rangeM / AiWeaponEnvelope.GUN_ASSUMED_MUZZLE_VEL_MPS
    leadPointWorld = target.pos + target.vel * timeOfFlightSec        // out-param Vec3Like, no allocation
    leadBearingRad = wrapPi(headingWorld(leadPointWorld - self.pos) - telemetry.headingRad)
    inEnvelope = target.rangeM in [GUN_MIN_RANGE_M, GUN_MAX_RANGE_M] and |leadBearingRad| <= GUN_MAX_ANGLE_OFF_DEG°
    quality = inEnvelope ? 1 - |leadBearingRad| / (GUN_MAX_ANGLE_OFF_DEG°) : 0
  case 'ir_missile':
    inEnvelope = target.rangeM in [IR_MIN_RANGE_M, IR_MAX_RANGE_M] and |target.bearingRad| <= IR_MAX_OFF_BORESIGHT_DEG°
    quality = inEnvelope ? 1 - |target.bearingRad| / (IR_MAX_OFF_BORESIGHT_DEG°) : 0
  case 'radar_missile':
    inEnvelope = target.rangeM in [RADAR_MIN_RANGE_M, RADAR_MAX_RANGE_M] and combat.lockState === RADAR_REQUIRED_LOCK
    quality = inEnvelope ? 1 : 0
```
`headingWorld(dx,dz) = atan2(dx, -dz)` (world heading of a relative vector, same formula as `HeadingFromVelocity`).

**Weapon selection (`out.cycleWeapon`)**: once per `BfmThresholds.MIN_STATE_DWELL_SEC`-sized window (reuse `timeInStateSec` crossing a multiple of 1.5 s, to avoid cycling every tick), if `ctx.combat.selectedWeapon` (`CombatStatus`, core.ts — the AI's own current selection, maintained by `src/combat`/`src/core` exactly as for the player, and always available without any AI-side tracking) is not the best `inEnvelope` weapon among gun/IR/radar against the current target (radar preferred at long range, then IR, then gun close in — i.e. prefer the weapon with the *longest* `AiWeaponEnvelope.*_MIN_RANGE_M` that is still `inEnvelope`), toggle `out.cycleWeapon = true` for exactly one tick (edge-triggered per core.ts).

**Firing (`out.trigger`)**: `out.trigger = weapon==='gun' && estimateWeaponEnvelope(ctx,'gun',target).inEnvelope && combat.ammoGun > 0 && (rngGaussian(this.rng) * difficulty.gunAccuracyErrorStdDeg <= AiWeaponEnvelope.GUN_MAX_ANGLE_OFF_DEG)` — the last clause re-samples the difficulty's aim-error distribution each tick as a hit-or-miss-style gate on top of the geometric envelope, so a `Rookie` (`gunAccuracyErrorStdDeg=3.0°`) squeezes the trigger less consistently than an `Ace` (`0.4°`) even when both are geometrically `inEnvelope`.

**Launching (`out.launch`)**: for the selected missile weapon, `out.launch = envelope.inEnvelope && ammoForWeapon(weapon) > 0 && missilesInFlightAtTarget(target.id) < difficulty.maxSimultaneousMissilesPerTarget && (ctx.simTimeSec - this.lastLaunchSimTimeSec) >= AiWeaponEnvelope.LAUNCH_COOLDOWN_SEC`. On the tick this evaluates true, also set `this.lastLaunchSimTimeSec = ctx.simTimeSec` (the AI does not itself track "missiles in flight" beyond this cooldown+ammo-delta heuristic — `missilesInFlightAtTarget` is approximated as 1 for `LAUNCH_COOLDOWN_SEC` after each launch at that target, 0 otherwise; a second, independent target can be engaged without waiting).

`out.cycleTarget` is edge-triggered `true` for one tick whenever `selectTarget` (4.5) returns a different `targetId` than last tick (keeps `ctx.combat`'s externally-visible "selected target" — maintained by `src/combat`/`src/core`, not this module — in sync with the AI's own internal choice).

### 4.10 Formation keeping (`formation.ts`)

```
headingFromVelocity(v) = |v| < ThreatWeights.MIN_SPEED_FOR_HEADING_MPS ? 0 : atan2(v.x, -v.z)

computeAspectAngleRad(observedHeadingRad, observedPos, observerPos):
  dx = observerPos.x - observedPos.x
  dz = observerPos.z - observedPos.z
  bearingObservedToObserverRad = atan2(dx, -dz)
  return wrapPi(bearingObservedToObserverRad - observedHeadingRad)

computeFormationTargetPos(leaderPos, leaderVelWorld, slot, out):
  h = headingFromVelocity(leaderVelWorld)
  forwardX = sin(h); forwardZ = -cos(h)
  rightX = cos(h);   rightZ = sin(h)
  out.x = leaderPos.x + rightX*slot.slotRightM - forwardX*slot.slotBackM
  out.y = leaderPos.y + slot.slotUpM
  out.z = leaderPos.z + rightZ*slot.slotRightM - forwardZ*slot.slotBackM
  return out
```
Worked example: `leaderPos=(1000,2000,500)`, `leaderVelWorld=(50,0,0)` (heading π/2, east) → `forward=(1,0,0)`, `right=(0,0,1)`; `slot={slotRightM:100, slotBackM:150, slotUpM:-20}` → `out = (1000 + 0*100 - 1*150, 2000-20, 500 + 1*100 - 0*150) = (850, 1980, 600)`.

When `formation?.role === 'wingman'`, `Patrol`/`Intercept`/`Rtb`'s goal builders replace the state's normal waypoint/patrol-anchor target with: find `formation.leaderId` in `ctx.contacts` (same-team formation-mates are always `identified: true` and visible at close range per `src/combat`'s sensor model); if found and alive, `desiredHeadingRad`-equivalent bank/speed are computed exactly as `Bfm`'s `PurePursuit` would against `computeFormationTargetPos(leaderContact.pos, leaderContact.vel, formation, scratchVec3)` treated as a stationary intercept point (`pitchMode = 'altitude_hold'`, `desiredAltitudeM = target.y`, `desiredBankRad` from the bearing to that point, `desiredSpeedMps = |leaderContact.vel|` matched to the leader's speed, clamped to `[80, 280]` m/s). If the leader is not found (dead, `leaderId === NO_ENTITY_ID`, or simply out of `saRadiusM`), the wingman falls back to flying its own independent `Patrol`/`Rtb` as if it had no `formation` at all — this is the module's one deliberately conservative assumption about module 10's spawn ordering; see section 9.

### 4.11 Landing / ILS approach (`landing.ts`)

**`resolveHomeRunway(ctx: PilotContext, homeAirportId: string | undefined, homeRunwayId: string | undefined): RunwayInfo | undefined`** — exported from `landing.ts` and imported by `tacticalFsm.ts` (rule 5, section 4.7) so both the FSM transition and the goal builder resolve "home" identically from the same optional spawn params:

```
airportId = homeAirportId ?? ctx.navDb.nearestAirport(self.pos)?.id
if airportId === undefined: return undefined            // no known/nearby airport at all
airport = navDb.getAirport(airportId)
runwayId = homeRunwayId ?? airport.runways[0]?.id        // first declared runway if unset
if runwayId === undefined: return undefined              // airport has no runways (malformed data)
return navDb.getRunway(airportId, runwayId)
```
This is the module's one fallback chain for a missing/unset `homeAirportId`/`homeRunwayId`: it never throws, and when it returns `undefined` (no `homeAirportId` and no airport within range of `nearestAirport`, or the resolved airport has no runways) rule 5 simply never fires — the AI stays in `Rtb`, indefinitely flying the `patrol.ts` Rtb cruise leg (section 4.12) toward the nearest-airport fallback position, rather than erroring or oscillating.

`Land`'s goal, built each tick from `resolveHomeRunway(ctx, homeAirportId, homeRunwayId)`:

```
runway = resolveHomeRunway(ctx, homeAirportId, homeRunwayId)   // RunwayInfo | undefined, core.ts
// runway is guaranteed defined here: rule 5 (section 4.7) only transitions into `Land` when resolveHomeRunway returned defined,
// and homeAirportId/homeRunwayId/navDb do not change after spawn, so buildLandingGoal is never called with an undefined runway.
ils = runway.ils                                        // IlsInfo | undefined
LOCALISER_CAPTURE_RANGE_M = 18000
GLIDESLOPE_CAPTURE_RANGE_M = 12000
FINAL_APPROACH_SPEED_MPS = 70
if ils and rangeToThreshold <= LOCALISER_CAPTURE_RANGE_M:
  desiredBankRad = ControlGains.HEADING_TO_BANK_KP * wrapPi(ils.localiserHeadingRad - telemetry.headingRad + bearingCorrectionFromOffsetLine)
  // bearingCorrectionFromOffsetLine nulls perpendicular distance from the localiser center-line the same way steerToGoal nulls bankErrorRad — a small P term
  // (PERP_CORRECTION_KP = 0.0006 rad per metre of perpendicular offset, clamped to +/-0.35 rad) added to the raw course error above.
  desiredAltitudeM = rangeToThreshold <= GLIDESLOPE_CAPTURE_RANGE_M
    ? runway.elevationM + rangeToThreshold * Math.tan(ils.glideslopeAngleRad)
    : telemetry.altMslM   // level until glideslope capture, do not dive early
else:
  // no ILS on this runway: straight-in visual approach at a fixed 3 degree geometric glideslope
  desiredBankRad = ControlGains.HEADING_TO_BANK_KP * wrapPi(runway.headingRad - telemetry.headingRad)
  desiredAltitudeM = runway.elevationM + rangeToThreshold * Math.tan(ILS_DEFAULT_GLIDESLOPE_RAD)  // core.ts constant, reused as the visual-approach angle
pitchMode = 'altitude_hold'
desiredSpeedMps = clamp(lerp(FINAL_APPROACH_SPEED_MPS, 180, clamp(rangeToThreshold / LOCALISER_CAPTURE_RANGE_M, 0, 1)), FINAL_APPROACH_SPEED_MPS, 180)
gearDown = rangeToThreshold < 5000
airbrake = rangeToThreshold < 8000 && telemetry.iasMps > FINAL_APPROACH_SPEED_MPS + 20
```
`rangeToThreshold = |self.pos - runway.thresholdPos|` (horizontal distance is sufficient given the shallow glideslope angles involved; using full 3-D distance is a negligible difference and avoids a second formula). Once `EntityFlag.OnGround` is set (from `self.flags`, core.ts), the goal switches to a ground roll: `pitchMode='g_load'`, `desiredGLoad=1`, `desiredBankRad=0`, `throttleOverride=0`, `desiredSpeedMps=0` (drives full braking via `steerToGoal`'s ground-brake rule, section 4.2) until `telemetry.iasMps < 5`, at which point the mission is considered complete for this AI (it stops producing meaningful further tactical transitions; `Land`'s FSM entry, rule 6, simply holds).

### 4.12 Patrol & RTB cruise legs (`patrol.ts`)

**Patrol** (non-wingman): maintain a circular racetrack around `patrolCenterWorld` at `patrolRadiusM` (default 8000 m if unset) and a cruise altitude of `patrolCenterWorld.y + 2000` (or `telemetry.altMslM` at first entry if `patrolCenterWorld.y` is 0/unset, to avoid a large unwanted altitude step): `bearingToTangentPointRad` is computed toward the point on the patrol circle 90° ahead of the aircraft's current bearing from the center (a standard "fly the circle" pursuit target), fed through the same bank formula as `PurePursuit`; `pitchMode='altitude_hold'`; `desiredSpeedMps = 180` (a fixed economical cruise speed); `gearDown=false, airbrake=false`.

**Rtb**: identical structure but the pursuit target is `airport.referencePos` where `airport = homeAirportId !== undefined ? navDb.getAirport(homeAirportId) : navDb.nearestAirport(self.pos)` (the same `homeAirportId ?? nearestAirport(self.pos)` fallback chain `resolveHomeRunway` (section 4.11) uses, applied here at the airport level since `Rtb`'s goal only needs a reference position, not a specific runway); if neither is available (no `homeAirportId` and no airport within range), the goal builder holds the aircraft's current heading and altitude instead (no waypoint to pursue) rather than crashing. `desiredAltitudeM = airport.elevationM + 3000`, `desiredSpeedMps = 220`.

**Intercept**: pursuit target is the selected threat contact's *current* position extrapolated 3 s ahead by its velocity (a simple lead so the AI closes rather than chases a stern-chase geometry at long range), `pitchMode='altitude_hold'`, `desiredAltitudeM = clamp(target.pos.y, telemetry.altMslM - 2000, telemetry.altMslM + 2000)` (close altitude gradually rather than instantly matching), `desiredSpeedMps = 250`.

### 4.12a `EngageBvr` goal (`tacticalFsm.ts`, `buildGoalForEngageBvr`)

Entered only once a valid BVR shot is possible (FSM rule 8, section 4.7: in radar-missile range, `combat.lockState==='locked'`, ammo available). The goal is to hold a STABLE tracking geometry so the radar lock and the already-launched (or about-to-launch) missile's guidance are not disturbed by aggressive manoeuvring — not to close aggressively:

```
pitchMode = 'altitude_hold'
desiredAltitudeM = clamp(target.pos.y, telemetry.altMslM - 1000, telemetry.altMslM + 1000)   // close altitude gently, tighter band than Intercept's 2000 m — a BVR shot wants a stable platform, not a climb/dive
bearingToTargetRad = target.bearingRad                                                        // target already resolved by selectTarget, section 4.5
desiredBankRad = clamp(ControlGains.HEADING_TO_BANK_KP * bearingToTargetRad, -ControlGains.MAX_MANOEUVRE_BANK_RAD, ControlGains.MAX_MANOEUVRE_BANK_RAD)
desiredSpeedMps = 220                                                                          // hold a stable BVR-employment speed, not a closing sprint
gearDown = false; airbrake = false
```

Weapon employment (section 4.9) runs unconditionally every tick regardless of `TacticalState` and is what actually fires the radar missile once `estimateWeaponEnvelope` says so — this goal only keeps the nose pointed at the target while that happens.

### 4.12b `Merge` goal (`tacticalFsm.ts`, `buildGoalForMerge`)

Entered between `BfmThresholds.VISUAL_MANOEUVRE_RANGE_M` (1800 m) and `ENGAGE_BVR_MIN_RANGE_M`/BVR-shot-unavailable range (FSM rules 8–10, section 4.7): the last visual gap before `Bfm`/`Defensive` takes over. Structurally identical to `PurePursuit` (section 4.8) but closes more aggressively and matches the target's altitude more tightly, since the goal here is to arrive at the merge with energy and a known target aspect, not to fly a sustained-turn BFM geometry yet:

```
pitchMode = 'altitude_hold'
desiredAltitudeM = clamp(target.pos.y, telemetry.altMslM - 500, telemetry.altMslM + 500)
desiredBankRad = clamp(ControlGains.HEADING_TO_BANK_KP * target.bearingRad, -ControlGains.MAX_MANOEUVRE_BANK_RAD, ControlGains.MAX_MANOEUVRE_BANK_RAD)
desiredSpeedMps = 280                                                                          // faster than Intercept's 250 — closing the last visual gap
gearDown = false; airbrake = false
```

`BfmThresholds.MERGE_RANGE_M` (3000 m, defined but otherwise only used as this state's own entry/exit boundary in FSM rules 9–10) is not additionally referenced inside this goal formula — it is purely a state-transition threshold, not a goal parameter.

### 4.12c `Disengage` goal (`tacticalFsm.ts`, `buildGoalForDisengage`)

Entered when fuel or ammo is critical (FSM rule 2, section 4.7), regardless of the previous state. The goal is unconditional, maximum-effort extension away from the nearest threat — structurally the same shape as `BreakTurn`'s bank/throttle pattern (section 4.8) but shallower-banked (opening range in a controllable direction, not out-turning an attacker) and always at full power:

```
pitchMode = 'g_load'
desiredGLoad = 1.0
desiredBankRad = Math.sign(target.bearingRad || 1) * BfmThresholds.DISENGAGE_BANK_RAD   // target = the nearest identified-hostile candidate, per section 4.5; turn away from it
desiredSpeedMps = telemetry.iasMps                                                       // irrelevant, overridden below
throttleOverride = 1.0
afterburnerOverride = true
gearDown = false; airbrake = false
```

If no identified-hostile candidate exists at all (target selection, section 4.5, returned `undefined`), `desiredBankRad = 0` (wings-level, straight-line extension — there is no threat bearing to turn away from). FSM rule 4 (section 4.7) transitions out of `Disengage` to `Rtb` once no hostile is within `DISENGAGE_SAFE_RANGE_M`, so this goal only needs to hold long enough to open that range, not navigate anywhere in particular.

### 4.13 Reaction delay & PRNG streams

Every `AiPilot` owns one private `mulberry32` state, seeded once at construction from `params.seed` (itself derived by `src/core` from `WorldConfig.seed` — never `Math.random`, per 00-architecture.md section 2). It is the sole source of: Gaussian gun-aim error samples (`gunAccuracyErrorStdDeg`), reaction-delay jitter samples, and `Jink`'s bank/g redraws. Two `AiPilot`s constructed with the same `seed` and fed bit-identical `PilotContext` sequences must produce bit-identical `PilotInputs` sequences (determinism, section 8).

**Perception delay** (`filterPerceived`, inside `pilotAi.ts`): a fixed-size `Float64Array(MAX_ENTITIES)` (`firstSeenSimTimeSec`, indexed by `unpackEntityId(contact.id).index`, pre-sized at construction — no per-tick allocation) records, for every currently-identified-hostile contact, the `simTimeSec` at which it was first seen as such. A contact is included in the array `filterPerceived` returns (itself a pre-sized, reused scratch array, entries overwritten and a live count tracked rather than `push`ed) only once `ctx.simTimeSec - firstSeenSimTimeSec[i] >= difficulty.reactionDelaySec + jitter_i`, where `jitter_i` is drawn once (Gaussian, `reactionJitterStdSec`) the first time that index is seen and cached alongside the timestamp. A contact that stops being a candidate (dies, loses identification) clears its slot (`firstSeenSimTimeSec[i] = -1`) so a later re-appearance is treated as new. `ctx.self`/`ctx.telemetry`/`ctx.combat`'s ammo counts are never delayed — a pilot always knows its own aircraft's state instantly; only *external* facts (new contacts, new warnings) are delayed. `missileWarningFirstSeenSimTimeSec`/`missileWarningNoticedAt` follow the identical one-shot-roll-then-cache pattern against `combat.missileInboundWarning` using `missileWarningNoticeProb` (rolled once per **tick** while unnoticed, not once per warning — a missile warning is urgent enough that the model gives repeated chances to notice it, unlike a slowly-developing contact).

## 6. Performance budget

`Pilot.update` runs once per `SIM_DT_SEC` (120 Hz) per AI-controlled aircraft. Budget: **≤ 0.05 ms per AI aircraft per tick on the "Medium" mobile-class device** (00-architecture.md's quality tiers govern rendering only, but this module still targets low-end hardware since it runs in the sim worker on every device). With up to ~8 simultaneous AI aircraft in a mission (a reasonable dogfight/strike-package scenario), that is ≤ 0.4 ms of the sim worker's 8.33 ms tick budget — leaving ample headroom for `src/physics` and `src/combat`.

To hit this:
- **Zero allocation after construction.** `FlightGoal` (`this.goal`, `this.terrainGoal`), the perceived-contacts scratch array, the `firstSeenSimTimeSec` typed array, and the `mulberry32` state are all allocated once in `createAiPilot`. `steerToGoal`, `computeTerrainAvoidanceGoal`, `scoreThreatContact`, `selectBfmManoeuvre`/`buildBfmGoal` take an `out`/scratch parameter or return a primitive/reused object — never `{...spread}`, never `.map`/`.filter` over `ctx.contacts` (use indexed `for` loops with an early `continue` for non-candidates).
- **O(contacts) per tick, bounded by `saRadiusM` filtering early.** `threatEvaluation`/`filterPerceived` do a single pass over `ctx.contacts` (already capped at `MAX_ENTITIES=400`, and in practice far fewer); the range check is the first comparison so non-candidates are skipped cheaply.
- **FSM/BFM selection is O(1)** — a fixed sequence of numeric comparisons, no loops, no string work in the hot path (the `TacticalState`/`BfmManoeuvre` `as const` string values are only compared by reference-equal string literals, which V8 interns — acceptable, matches core.ts's own `EntityKind`-style pattern).
- **PRNG draws are O(1)** (`mulberry32` is a single 32-bit integer step); Gaussian sampling uses a Box-Muller pair cached across two calls (one `mulberry32` step produces two uniform samples per Gaussian pair, one used immediately, one cached for the next call) to avoid wasting draws — implemented in `src/ai`, not `src/math`, since it is AI-specific enough not to belong in the shared math library's general-purpose surface (module 01 was not asked for a Gaussian sampler).
- **`HeightSampler.heightAt` calls are the dominant per-tick cost** (5–40 calls per aircraft per tick from terrain avoidance, distance-adaptive per section 4.4 — `SAMPLE_COUNT_MAX = 40` bounds the worst case at high speed/long lookahead, i.e. up to 320 calls/tick across 8 simultaneous AI aircraft at full speed) — this module treats `heightAt` as O(1) amortized per 00-architecture.md's determinism/purity guarantee and does not cache results across ticks (module 04's own spec is responsible for `heightAt`'s own performance budget; a typical mission has most AI aircraft below full BFM speed most of the time, so 320/tick is a conservative worst case, not the steady-state cost).

## 9. Open assumptions

- **No access to `AircraftDefinition`.** This module never imports `contracts/aircraft.ts` or `contracts/combat.ts`. Consequently `maxCommandedGLoad`/`minCommandedGLoad` (section 5.1) are fixed, difficulty-scaled absolute g values chosen to be plausible for a modern light fighter, **not** derived from the Tejas's real structural limits (which live in module 03's `FcsLimits`, unknown to this drafter) — the real FCS clamps independently regardless, so this cannot cause an over-stress, only a slightly conservative or slightly optimistic AI compared to the jet's true envelope. Similarly, `AiWeaponEnvelope`'s gun/IR/radar range and angle figures (section 5.5) are the AI's own approximate mental model, analogous to GSh-23 (gun), Python-5-class (IR) and Derby/Astra-Mk1-class (radar) missiles — the closest public analogues to Tejas Mk1's actual (partly classified/sparse) weapons fit — and are deliberately conservative "commit range" estimates rather than each weapon's absolute maximum reach, since a pilot (real or AI) does not fire at the extreme edge of a weapon's envelope by choice.
- **`contracts/math.ts` not imported.** Per this file's own header, `contracts/ai.ts` uses only `core.ts`'s `Vec3Like` and never imports a concrete `Vec3`/`Quat`/`Mat3` type from `./math`, because this drafter has not seen module 01's actual export names, only 00-architecture.md's prose description of them. `src/ai`'s *implementation* is expected to use the real `src/math` classes (mutable, `out`-param) internally and the real `mulberry32`/Gaussian-from-uniform sampling described in section 4.13/6 — only the contract's own compile-time surface avoids the dependency.
- **`Contact` carries no orientation field.** `core.ts`'s `Contact` interface has `pos`/`vel` but no heading/quaternion for the observed aircraft, so every place this module needs another aircraft's orientation (`aspectAngleRad`, formation slot rotation, BVR-envelope geometry) derives it from `Contact.vel` via `headingFromVelocity` (section 4.10) — a coordinated-flight approximation (assumes negligible sideslip on the *observed* aircraft) that is realistic in the same sense a real pilot cannot see another cockpit's exact orientation either, only infer it from the other aircraft's flight path.
- **Formation leader spawn order.** `AiFormationSlot.leaderId` (section 4 of `contracts/ai.ts`) assumes `src/core` spawns a `MissionAiFlight`'s formation leader before its wingmen, so each wingman's `AiPilotSpawnParams.formation.leaderId` is a valid, already-known `EntityId` at construction time. This is not pinned anywhere in `00-architecture.md` (it is not a cross-module data *shape*, just a sequencing expectation on module 10), so per this document's own instructions this module treats it as the conservative default and is fully robust to it being wrong: an invalid/dead `leaderId` degrades to independent flight (section 4.10, acceptance criterion 8) rather than erroring, so an incorrect assumption here costs formation realism, never correctness.
- **No countermeasures.** `core.ts`'s `PilotInputs` has no chaff/flare field, so this module's only defence against `combat.missileInboundWarning` is manoeuvring (`Notch`/`BreakTurn`) — matching the actual scope of what `PilotInputs` can express, not an oversight.
- **BFM manoeuvre geometry is 2-D-bank-plus-g, not full 3-D pursuit.** Real BFM reasons about the pursuer's *lift-vector* orientation in 3-D relative to the target; this module's `FlightGoal` only expresses a body-frame bank angle and a scalar g-load (section 4.8's High/Low-Yo-Yo rationale), which is materially simpler than a real fire-control-quality pursuit model but is judged an acceptable and clearly-documented simplification for a game AI whose brief asks for named, recognisable manoeuvres and threat-appropriate behaviour, not flight-test-grade optimality.
- **Control gains (`ControlGains`, `BfmThresholds`) are first-pass defaults, not flight-tuned.** They were chosen to be dimensionally sound, stable (damped, clamped) and to produce the worked numeric examples in section 4 and the tests in section 7, not derived from any Tejas flight-test or simulator data (none of which this drafter has access to). They are still part of the contract (exported constants other tests key off), so changing them later is a contract change, but their *initial* values are an engineering judgement call, flagged here per this project's "no TBD, but flag approximations" rule.
- **Missile-in-flight tracking is approximate.** `PilotContext` does not tell the AI how many of its own missiles are currently in flight against a given target (that is `src/combat`'s internal state). Section 4.9's `missilesInFlightAtTarget` is therefore approximated purely from this `AiPilot`'s own `lastLaunchSimTimeSec`/`LAUNCH_COOLDOWN_SEC` window rather than a true in-flight count — sufficient to satisfy `maxSimultaneousMissilesPerTarget`'s intent (do not dump the whole magazine into one salvo) without needing data this module was not given.
