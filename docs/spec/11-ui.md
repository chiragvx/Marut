# 11 — UI, Quality Tiers, Airport Editor, PWA

Module 11. Implements `docs/spec/contracts/ui.ts`. Read `00-architecture.md` and `contracts/core.ts` in full before this document; where anything here appears to disagree with either, they win (see `00-architecture.md` §1). This document does not restate coordinate/unit conventions from `00-architecture.md` §3 except where a formula below depends on them directly (world-frame X/Z plane, heading convention, `forwardWorld(heading)`).

## 1. Purpose & scope

Module 11 owns everything a human sees and clicks that is **not** the in-flight HUD (module 08) and **not** raw input capture (module 09): the main menu, mission select, settings (including control rebinding and quality override), the pause menu, the mission debrief screen, the first-run loading screen, a mobile landscape-orientation prompt, automatic graphics quality-tier detection (GPU string heuristic + a 2-second WebGL benchmark + device-pixel-ratio), the in-browser 2D top-down airport editor (place/drag/rotate runways, draw taxiways and aprons, set ILS, live validation, JSON import/export, a shareable URL-hash encoding, and launching a mission directly from the edited layout), and the PWA manifest + service worker.

Everything in this module is plain DOM + Canvas 2D + raw WebGL (for the benchmark only) — no UI framework, no Three.js, no other runtime dependency, per `00-architecture.md` §2. Module 11 does not decide screen *navigation* (which screen is shown when, what happens on mission end) — that is `src/core`'s app-state machine (module 10); this module fixes only how each screen is constructed, what data it needs, and what it emits.

Module 11 does not implement what a `QualityTier` value controls in rendering (draw distance, shadows, AA, HUD contact cap, ...) — that table is normative in `00-architecture.md` §14 and is module 08/10's job to honour. Module 11 only *selects* the `QualityTier` value.

## 4. Design & algorithms

### 4.1 Shared screen-mount helper

`src/ui/screenHandle.ts` exports one internal helper used by every `CreateX` factory:

```ts
function mountScreen(container: HTMLElement, rootEl: HTMLElement): ScreenHandle {
  rootEl.classList.add('tj-screen');
  container.appendChild(rootEl);
  let destroyed = false;
  return {
    rootEl,
    show() { rootEl.classList.remove('tj-hidden'); },
    hide() { rootEl.classList.add('tj-hidden'); },
    destroy() {
      if (destroyed) return;
      destroyed = true;
      rootEl.replaceChildren(); // drop all listeners attached to descendants
      rootEl.remove();
    },
  };
}
```

`.tj-hidden { display: none; }` is the only CSS class this contract depends on for correctness; each screen module may add its own scoped classes for layout, but `tj-hidden`'s effect must be exactly `display:none` so `tests/ui/screens.test.ts` can assert visibility via `getComputedStyle`/class presence without a real layout engine. `destroy()` calling `rootEl.replaceChildren()` before `.remove()` is required so any `addEventListener` closures on descendants are eligible for GC even if a test harness keeps a reference to a detached node.

**Testable DOM hook convention.** Every clickable control in every screen carries a `data-action="<verb>"` attribute so tests (and this spec) can address it without depending on visible text or CSS classes:

| screen | `data-action` values |
|---|---|
| main menu | `play`, `airport-editor`, `settings` |
| mission select | `launch`, `back` (+ one row per mission, each `<li data-mission-id="...">` with an inner `data-action="launch"` button; a `<select data-action="difficulty">` with `<option>` values exactly `AiDifficulty`'s three string values) |
| settings | `back`, `reset-defaults`, `quality-override` (a `<select>` with options `auto`,`low`,`medium`,`high`,`ultra`), and one `data-action="rebind"` button per binding row carrying `data-binding-action="<BindableAction value>"` |
| pause | `resume`, `restart`, `quit-to-menu`, `open-settings` |
| debrief | `replay`, `mission-select`, `main-menu` |
| airport editor toolbar | `select`, `add-runway`, `add-taxiway`, `add-apron`, `set-ils`, `remove-ils`, `delete`, `finish-shape`, `cancel-shape`, `export`, `import`, `copy-link`, `test-fly`, `exit`, plus `snap` (cycles `EDITOR_SNAP_OPTIONS_M`, §4.5) |

### 4.2 Quality tier detection

`DetectQualityTier(canvas)` is pure composition:

```ts
async function detectQualityTier(canvas: HTMLCanvasElement): Promise<QualityTierReport> {
  const dpr = Math.min(window.devicePixelRatio || 1, DEVICE_PIXEL_RATIO_CAP);
  canvas.width = Math.round(BENCHMARK_CANVAS_CSS_WIDTH_PX * dpr);
  canvas.height = Math.round(BENCHMARK_CANVAS_CSS_HEIGHT_PX * dpr);
  const { renderer, vendor } = readWebglRendererStrings(canvas);
  const gpu = classifyGpuRenderer(renderer, vendor);
  const benchmark = await runRenderBenchmark(canvas, BENCHMARK_DURATION_MS, BENCHMARK_WARMUP_MS, BENCHMARK_TRIANGLE_COUNT);
  return computeQualityTier(gpu, benchmark, dpr);
}
```
`BENCHMARK_CANVAS_CSS_WIDTH_PX = 480`, `BENCHMARK_CANVAS_CSS_HEIGHT_PX = 270` (internal constants of `benchmark.ts`, not part of the public contract since callers never size the canvas themselves — `detectQualityTier` owns the only call site). The canvas passed to `DetectQualityTier` must be detached (never appended to `document`) so the benchmark never triggers a paint.

**GPU string classification** (`classifyGpuRenderer`, pure, case-insensitive substring match on the lower-cased `rendererString` only — `vendorString` is carried through into `GpuInfo.vendor` for diagnostics but is not itself scored, since `UNMASKED_VENDOR_WEBGL` values are far less specific than the renderer string):

```
lower = rendererString.toLowerCase()
if lower contains any of WEAK_GPU_TOKENS  -> strengthHint = 'weak'
else if lower contains any of STRONG_GPU_TOKENS -> strengthHint = 'strong'
else -> strengthHint = 'unknown'
```
Weak is checked **before** strong so a software renderer string that happens to also mention a real GPU name (e.g. a VM's "SwiftShader (fallback for Intel HD)") is still classified weak. Token tables are §5.1/§5.2.

**Benchmark** (`runRenderBenchmark`, impure, §5.3 gives the exact shader/loop): renders `triangleCount` static triangles (one `gl.TRIANGLES` draw call per `requestAnimationFrame` callback) for `durationMs` wall-clock, discards samples from the first `warmupMs`, and returns:
```
avgFrameMs = sum(measured frame deltas) / samples
fps = 1000 / avgFrameMs
```
If `canvas.getContext('webgl2')` and `canvas.getContext('webgl')` both fail (return `null`), resolve immediately with `{ avgFrameMs: 0, fps: 0, samples: 0 }` — never throw, never reject.

**Score → tier** (`computeQualityTier`, pure):

| input | condition | score |
|---|---|---|
| GPU | `strengthHint === 'strong'` | `+2` |
| GPU | `strengthHint === 'weak'` | `-2` |
| GPU | `strengthHint === 'unknown'` | `0` |
| benchmark | `fps >= QUALITY_BENCHMARK_FPS_THRESHOLDS.ULTRA` (55) | `+3` |
| benchmark | `fps >= .HIGH` (40) | `+2` |
| benchmark | `fps >= .MEDIUM` (25) | `+1` |
| benchmark | else | `0` |

`combined = gpuScore + benchmarkScore` (range `[-2, 5]`).

| `combined` | tier |
|---|---|
| `<= 0` | `low` |
| `1, 2` | `medium` |
| `3, 4` | `high` |
| `>= 5` | `ultra` |

`reasons` is built by pushing one string per contributing factor in this order: GPU classification (`"gpu: <renderer> -> <strengthHint> (<+2|0|-2>)"`), benchmark (`"benchmark: <fps.toFixed(1)>fps -> <bucket> (<score>)"`), DPR (`"devicePixelRatio: <raw> capped to <capped>"`), final tier (`"combined score <combined> -> <tier>"`). `devicePixelRatioCapped` does not itself enter the score — it already shaped the benchmark's measured fps because the benchmark canvas was sized by it (§4.2 first code block) — but is still surfaced on `QualityTierReport` because module 08/10 need it independently to cap their own WebGL renderer's output resolution (per `00-architecture.md` §14, "target render FPS" per tier), not just for tier selection.

Worked example: `strengthHint:'strong'`, `fps=60` (samples=90 over the 1500 ms measured window at ~16.7 ms/frame) → gpuScore `+2`, benchmarkScore `+3` (60≥55) → combined `5` → `ultra`.

### 4.3 Settings screen

`SettingsState.onChange` fires on: quality-override `<select>` change, every rebind commit, mouse-sensitivity slider `change` event (not `input` — i.e. on release, not per pixel dragged), invert-pitch checkbox change. It never fires while a number field has uncommitted keystrokes.

Rebind flow: clicking a `data-action="rebind"` button calls `callbacks.onRebindStart(action)` and puts that row into a "press any key…" visual state; the row's own button becomes non-actionable until `setCapturedKey(action, code)` is called by the owner (module 10, which is the one actually listening to `keydown` via whatever `src/input` exposes) or 5000 ms elapse with no call, at which point the row reverts and no binding changes. `setCapturedKey` overwrites any existing `KeyBinding` for that `action` (one binding per action; this module does not support chords or multiple keys per action) and immediately fires `onChange` with the updated `keyBindings` array (a new array; `KeyBinding` objects themselves are not mutated in place, consistent with `SettingsState` being a plain data snapshot the caller owns).

**Persistence.** `src/ui/settings.ts` performs **no** `localStorage`/IndexedDB I/O. `initial: SettingsState` is supplied by the caller (module 10) on every `CreateSettingsScreen` call, and `onChange` hands the caller a full new `SettingsState` to persist however it chooses. This keeps module 11 purely presentational and avoids a second, hidden source of truth for settings state (see §9).

### 4.4 Main menu, mission select, pause, debrief, loading, orientation prompt

These five screens plus the orientation prompt hold no algorithmic complexity beyond the DOM-construction/testable-hook rules of §4.1; their behaviour is fully specified by their contract signatures (§3) plus:

- **Mission select**: the difficulty `<select>` initial value is `options.defaultDifficulty`; `callbacks.onLaunch(missionId, difficulty)` reads the currently selected row's `data-mission-id` and the `<select>`'s current value at the moment `data-action="launch"` is activated (not the value at mount time).
- **Debrief**: renders `stats.objectivesCompleted.length / stats.objectivesTotal` as a fraction plus a per-shot accuracy line `stats.shotsHitGun / max(1, stats.shotsFiredGun)` and `stats.missilesHit / max(1, stats.missilesFired)` (the `max(1, …)` guard avoids a `0/0` `NaN` display when no shots were fired — this is display-only arithmetic, not written back anywhere).
- **Loading screen**: `setProgress(fraction, message)` clamps `fraction` to `[0,1]` internally (`Math.min(1, Math.max(0, fraction))`) before writing it to a `<progress>` element's `value`; `message`, when given, replaces a single `<span data-role="loading-message">`'s `textContent`; when omitted the previous message is left unchanged (never cleared).
- **Orientation prompt**: `mountOrientationPrompt(container)` appends a full-viewport (`position:fixed; inset:0`) overlay that is visible exactly when both `matchMedia('(orientation: portrait)').matches` is true AND `Math.max(window.screen.width, window.screen.height) <= MOBILE_MAX_DIMENSION_PX` (900) is true, re-evaluated on the `matchMedia` list's `change` event (registered via `addEventListener('change', …)`) and on `window.addEventListener('resize', …)`. The overlay is advisory only: it never sets `pointer-events` to block interaction underneath it (a player who ignores it can still fly). `destroy()` removes both listeners and the overlay element.

### 4.5 Airport editor

**State owned internally by `airportEditor.ts`** (not part of the contract — no external consumer needs to read it): `panXM, panZM: number` (world position at canvas center), `pixelsPerMeter: number`, `mode: 'select' | 'add-runway' | 'add-taxiway' | 'add-apron'`, `snapM: number` (current member of `EDITOR_SNAP_OPTIONS_M`), `selection` (none / a runway id + optional end / a taxiway id + optional point index / an apron id + optional point index), `draftPoints: EditorPoint[]` (in-progress taxiway/apron), and the current `EditorAirportLayout` (mutated in place by committed edits, read via `getLayout()` which returns a **structural-clone deep copy**, never the live internal object, so a caller mutating the returned value cannot corrupt editor state).

`EDITOR_SNAP_OPTIONS_M = [0, 1, 5, 10] as const` (metres), default index `1` (i.e. 1 m snap). `snappedM(v, snapM) = snapM === 0 ? v : Math.round(v / snapM) * snapM`, applied independently to `xM`/`zM` (or to a computed `widthM`/`lengthM`) of every committed pointer interaction below.

**Coordinate transform** (canvas CSS pixel size `wPx × hPx`):
```
worldToScreen(xM, zM) = {
  sx: wPx/2 + (xM - panXM) * pixelsPerMeter,
  sy: hPx/2 + (zM - panZM) * pixelsPerMeter,
}
screenToWorld(sx, sy) = {
  xM: panXM + (sx - wPx/2) / pixelsPerMeter,
  zM: panZM + (sy - hPx/2) / pixelsPerMeter,
}
```
This makes screen-up = world `-Z` = north, matching `00-architecture.md` §3.1's heading convention directly (heading 0 = north = up on the editor canvas, increasing clockwise = matches on-screen clockwise rotation — no extra sign flip needed anywhere in the editor).

**Pan/zoom**: `pointerdown` with the primary pointer on empty canvas (no handle under the cursor, §4.5.2) starts a pan; `panXM`/`panZM` are decremented by the pointer's screen-space movement converted through the *current* `pixelsPerMeter` on every `pointermove` while the pointer is captured (`setPointerCapture`). `wheel` zooms, centred on the cursor:
```
before = screenToWorld(cursorSx, cursorSy)
pixelsPerMeter = clamp(pixelsPerMeter * 1.1^(-deltaY/100), MIN_PPM, MAX_PPM)   // MIN_PPM=0.5, MAX_PPM=20 (px/m)
panXM = before.xM - (cursorSx - wPx/2) / pixelsPerMeter
panZM = before.zM - (cursorSy - hPx/2) / pixelsPerMeter
```
so the world point under the cursor is unchanged by the zoom.

**Grid**: candidate step metres `[1,5,10,25,50,100,250,500,1000,2500,5000]`; draw the smallest candidate `g` with `g * pixelsPerMeter >= 40` (px); if none qualifies (extremely zoomed out) use `5000`. Every 5th grid line (index multiple of 5 from world origin) is drawn at double opacity as a "major" line.

#### 4.5.1 Runway axes

For a runway with `headingRad`, its two local unit axes in the world X/Z plane are:
```
forward = ( sin(headingRad), -cos(headingRad) )   // matches forwardWorld() from 00-architecture.md §3.1, X/Z components
right   = ( cos(headingRad),  sin(headingRad) )   // = forward rotated +90°, matches heading's clockwise-positive sense
```
Handle world positions (`halfLen = lengthM/2`, `halfWid = widthM/2`):
```
center        = (centerXM, centerZM)
endPrimary    = center + forward * halfLen
endReciprocal = center - forward * halfLen
sideA         = center + right * halfWid
sideB         = center - right * halfWid
```

#### 4.5.2 Pointer-driven editing (mode = `select`)

Hit-testing radius: `HANDLE_HIT_RADIUS_PX = 10` for mouse/pen pointers, `TOUCH_HANDLE_HIT_RADIUS_PX = 18` for `event.pointerType === 'touch'` (checked per-event, so the same session works correctly with a mouse and a touchscreen interchangeably). All pointer handling uses the Pointer Events API (`pointerdown`/`pointermove`/`pointerup`/`pointercancel`) exclusively — no separate `mouse*`/`touch*` handlers — so mouse, touch and pen share one code path.

On `pointerdown`, hit-test in this priority order (first match wins): a runway's `endPrimary`/`endReciprocal` handle (selects that runway **and** that end — required before "Set ILS" is enabled) → a runway's `sideA`/`sideB` handle → a runway's `center` → a taxiway/apron point handle of the currently-selected feature → any runway body (point-in-oriented-rectangle test using the same axes as §4.5.1) → any apron body (point-in-polygon via the standard ray-casting test) → empty space (pan, or in an `add-*` mode, place/append a point).

Drag math while the pointer is captured, per handle kind:

- **Center handle** (move): `center = snapped(screenToWorld(pointer))`. `headingRad`/`lengthM`/`widthM` unchanged.
- **End handle** (resize + rotate together — this is the *only* rotate gesture the editor has; there is no separate rotate gizmo): let `fixed` = the *other* end's current world position (unchanged by this drag). `raw = snapped(screenToWorld(pointer)) - fixed`. `newLength = clamp(|raw|, EDITOR_RUNWAY_LENGTH_MIN_M, EDITOR_RUNWAY_LENGTH_MAX_M)`. `dir = raw / |raw|`. `center = fixed + dir * newLength/2`. `headingRad = wrap0to2pi(atan2(dir.x, -dir.z))` (inverse of `forward()` in §4.5.1). `lengthM = newLength`.
- **Side handle** (width only): `halfWid = clamp(dot(screenToWorld(pointer) - center, right), EDITOR_RUNWAY_WIDTH_MIN_M/2, EDITOR_RUNWAY_WIDTH_MAX_M/2)`, then snapped: `widthM = snappedM(2*halfWid, snapM)`. `center`/`headingRad`/`lengthM` unchanged.
- **Taxiway/apron point handle**: that point's `xM`/`zM` set to `snapped(screenToWorld(pointer))`.

On `pointerup`, if the drag moved the pointer by more than `4` px from its `pointerdown` position, the mutation is committed (layout updated, `ValidateEditorLayout` re-run, `callbacks.onChange?.(getLayout())` fired); otherwise (a plain click, not a drag) it is treated as a **selection** click only — no mutation, no `onChange`.

#### 4.5.3 Placement modes

- `add-runway`: next `pointerup` that was not a drag (≤4px movement) creates `{ id:"runway-"+(runwayCounter++), centerXM, centerZM: snapped(screenToWorld(pointer)), headingRad:0, lengthM:2500, widthM:45, elevationM: layout.elevationM }`, appends it, selects it (mode reverts to `select`).
- `add-taxiway` / `add-apron`: each non-drag `pointerup` appends a snapped point to `draftPoints`. `data-action="finish-shape"` is enabled once `draftPoints.length >= 2` (taxiway) or `>= 3` (apron); activating it commits `{ id: "taxiway-"+(taxiwayCounter++), widthM:20, points:[...draftPoints] }` or `{ id:"apron-"+(apronCounter++), elevationM: layout.elevationM, points:[...draftPoints] }`, clears `draftPoints`, reverts mode to `select`. `data-action="cancel-shape"` or the `Escape` key discards `draftPoints` without committing.
- `*Counter` (runway/taxiway/apron) are per-editor-session integers starting at `1`, **only ever incremented**, never reused after a delete — guarantees id stability/uniqueness for the life of the editing session.

`data-action="delete"` removes the currently-selected whole feature (runway, or the selected taxiway/apron) after a native `confirm()`-style inline confirmation row (rendered in the toolbar, not a blocking `window.confirm`, so it stays testable via `data-action="delete"` twice: once to arm, once to confirm — this two-step pattern is the one exception to "every `data-action` fires immediately", noted here explicitly to avoid ambiguity). Deleting a single point from an existing taxiway/apron (as opposed to the whole feature) is only offered when the feature has more points than its minimum (2 for taxiway, 3 for apron); otherwise the point-delete control is not rendered at all.

#### 4.5.4 ILS assignment

Enabled only when the current selection is a runway **end** (§4.5.2's end-handle selection, not a body/center selection). `data-action="set-ils"` opens an inline form pre-filled with `frequencyMhz: 110.30`, `glideslopeAngleRad: 0.05236` (`ILS_DEFAULT_GLIDESLOPE_RAD` from `core.ts`, shown to the user in **degrees** — `glideslopeAngleRad * 180/Math.PI` — per `00-architecture.md` §2's "degrees only in UI display" rule, converted back to radians on commit); confirming writes the result into `ilsPrimary` (if `endPrimary` selected) or `ilsReciprocal` (if `endReciprocal` selected). `data-action="remove-ils"` is rendered only when the selected end already has an ILS, and clears it to `undefined`.

#### 4.5.5 Validation, geometry helpers

`RunwayDesignator(headingRad)`:
```
deg = ((headingRad * 180/Math.PI) % 360 + 360) % 360
num = Math.round(deg / 10) % 36
if (num === 0) num = 36
return String(num).padStart(2, '0')
```
Used for `primaryDesignator = RunwayDesignator(r.headingRad)` and `reciprocalDesignator = RunwayDesignator(r.headingRad + Math.PI)`.

`RectanglesOverlap(a, b)` — 2D oriented-bounding-box separating-axis test, testing the 4 candidate axes (each rectangle's own `forward`/`right` from §4.5.1, reconstructed from `a.headingRad`/`b.headingRad`):
```
for axis in [forwardA, rightA, forwardB, rightB]:
  d  = dot(bCenter - aCenter, axis)
  ra = a.halfLengthM*|dot(forwardA,axis)| + a.halfWidthM*|dot(rightA,axis)|
  rb = b.halfLengthM*|dot(forwardB,axis)| + b.halfWidthM*|dot(rightB,axis)|
  if |d| > ra + rb: return false   // this axis separates them
return true   // no separating axis found -> overlapping
```

`PolygonAreaM2(points)` — shoelace, absolute value:
```
area = 0.5 * |Σ_{i=0..n-1} (points[i].xM * points[(i+1)%n].zM - points[(i+1)%n].xM * points[i].zM)|
```

`PolygonCentroid(points, out)` — vertex average (a declared approximation of the true area centroid, §9): `out.xM = mean(points[].xM)`, `out.zM = mean(points[].zM)`, returns `out`.

`ComputeFlattenZones(layout)` — one zone per runway plus one per apron (taxiways never generate a zone: they are assumed to follow natural/already-flattened terrain between flattened features, consistent with `00-architecture.md` §9.2 leaving multi-zone blending to module 04):
```
for each runway r:
  emit { centerWorldX: r.centerXM, centerWorldZ: r.centerZM, elevationM: r.elevationM,
         flatRadiusM: hypot(r.lengthM/2, r.widthM/2) + RUNWAY_FLATTEN_MARGIN_M (15),
         blendRadiusM: RUNWAY_FLATTEN_BLEND_M (40) }
```

### 4.6 Validation rules

| # | severity | condition (issue raised when true) | `featureType` | message template |
|---|---|---|---|---|
| 1 | error | `runway.lengthM < 500 or > 5000` | runway | `"runway {id} length {lengthM}m outside [500,5000]m"` |
| 2 | error | `runway.widthM < 20 or > 80` | runway | `"runway {id} width {widthM}m outside [20,80]m"` |
| 3 | error | two runways share the same `id` | runway | `"duplicate runway id {id}"` |
| 4 | error | `RectanglesOverlap` true for any runway pair | runway | `"runway {id1} overlaps runway {id2}"` |
| 5 | error | `runway.ils*.frequencyMhz < 108.10 or > 111.95` | runway | `"runway {id} ILS frequency {f}MHz outside [108.10,111.95]MHz"` |
| 6 | warning | frequency in range but not a multiple of `0.05` MHz (within `1e-6`) | runway | `"runway {id} ILS frequency {f}MHz is not on a 0.05MHz channel"` |
| 7 | error | `runway.ils*.glideslopeAngleRad < 0.0349 or > 0.0698` | runway | `"runway {id} ILS glideslope {deg}° outside [2°,4°]"` |
| 8 | error | `taxiway.points.length < 2` | taxiway | `"taxiway {id} has fewer than 2 points"` |
| 9 | error | `apron.points.length < 3` | apron | `"apron {id} has fewer than 3 points"` |
| 10 | warning | `PolygonAreaM2(apron.points) < 100` | apron | `"apron {id} area {a}m² is very small"` |
| 11 | error | two taxiways or two aprons (checked within each type separately) share the same `id` | taxiway/apron | `"duplicate {featureType} id {id}"` |
| 12 | error | `layout.runways.length === 0` | airport | `"airport must have at least one runway"` |
| 13 | error | `layout.id` fails `[a-z0-9-]` charset or length outside `[2,40]` | airport | `"airport id must be 2-40 lowercase letters, digits or hyphens"` |
| 14 | error | `layout.name` empty or longer than `80` chars | airport | `"airport name must be 1-80 characters"` |

Rules 1/2/5/7 read `ils*` as "each of `ilsPrimary` and `ilsReciprocal` that is present," producing up to two separate issues per runway. All 14 rules run unconditionally and independently (no short-circuiting) so `ValidateEditorLayout` always returns the *complete* issue set for the current layout in one pass — the editor's live-validation panel lists all of them at once, not one-at-a-time.

### 4.7 Import / export / URL hash

**Export.** `ExportEditorLayout(layout)`:
1. `flattenZones = ComputeFlattenZones(layout)` (always freshly derived — never read from any stored/previous value).
2. Build a plain object literal in **exactly** this key order (object literal insertion order is what determines `JSON.stringify` key order for string keys; no replacer array needed):
   `formatVersion, id, name, referenceXM, referenceZM, elevationM, runways, taxiways, aprons, flattenZones` — and within each runway: `id, centerXM, centerZM, headingRad, lengthM, widthM, elevationM, ilsPrimary, ilsReciprocal, primaryDesignator, reciprocalDesignator`.
3. `JSON.stringify(obj, null, 2)`.

**Import.** `ImportEditorLayout(json)`:
1. `JSON.parse` in a `try/catch`; a throw returns `{ ok:false, error:"invalid JSON: <message>" }`.
2. Check `parsed.formatVersion === EDITOR_LAYOUT_FORMAT_VERSION` (`1`); mismatch (including missing) returns `{ ok:false, error:"unsupported formatVersion <value>, expected 1" }`.
3. Build an `EditorAirportLayout` by reading only `id, name, referenceXM, referenceZM, elevationM, runways[].{id,centerXM,centerZM,headingRad,lengthM,widthM,elevationM,ilsPrimary,ilsReciprocal}, taxiways, aprons` — **any other top-level or per-runway keys present (`flattenZones`, `primaryDesignator`, `reciprocalDesignator`) are read and discarded, never copied into the returned value and never causing rejection.** This is what lets `ImportEditorLayout` accept both `ExportEditorLayout`'s output and `EncodeLayoutToUrlHash`'s underlying JSON (§ below) through one code path.
4. Missing/wrong-typed required fields (any of `id`,`name`,`elevationM`,`runways`,`taxiways`,`aprons` absent, or a numeric field that is not `typeof === 'number'`/finite) returns `{ ok:false, error:"missing or invalid field <path>" }` immediately (structural check, before running `ValidateEditorLayout`).
5. Run `ValidateEditorLayout` on the built object; if any issue has `severity:'error'`, return `{ ok:false, error: issues.filter(i=>i.severity==='error').map(i=>i.message).join('; ') }`. Warnings do not block import.
6. Otherwise return `{ ok:true, value: <built object> }`.

**URL hash.** `EncodeLayoutToUrlHash`/`DecodeLayoutFromUrlHash` operate on the **same reduced shape** as step 3 above (`{formatVersion:1, ...EditorAirportLayout fields}`, *not* the heavier `EditorAirportLayoutExport` with derived `flattenZones`/designators) — a share link is meant to resume editing, not to carry redundant derived data:
```ts
function bytesToBase64Url(json: string): string {
  const bytes = new TextEncoder().encode(json);
  let binary = '';
  for (let i = 0; i < bytes.length; i++) binary += String.fromCharCode(bytes[i]);
  return btoa(binary).replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}
function base64UrlToBytes(hash: string): Uint8Array {
  let b64 = hash.replace(/^#/, '').replace(/-/g, '+').replace(/_/g, '/');
  while (b64.length % 4 !== 0) b64 += '=';
  const binary = atob(b64);
  const bytes = new Uint8Array(binary.length);
  for (let i = 0; i < binary.length; i++) bytes[i] = binary.charCodeAt(i);
  return bytes;
}
```
`EncodeLayoutToUrlHash(layout) = bytesToBase64Url(JSON.stringify({ formatVersion: EDITOR_LAYOUT_FORMAT_VERSION, id: layout.id, name: layout.name, referenceXM: layout.referenceXM, referenceZM: layout.referenceZM, elevationM: layout.elevationM, runways: layout.runways, taxiways: layout.taxiways, aprons: layout.aprons }))`. `DecodeLayoutFromUrlHash(hash)` reverses via `new TextDecoder().decode(base64UrlToBytes(hash))` then runs the exact same steps 1–6 as `ImportEditorLayout` on the resulting JSON string (it is implemented as a thin wrapper: `decodeLayoutFromUrlHash = (hash) => importEditorLayout(textDecode(base64UrlToBytes(hash)))`). A malformed base64url string makes `atob` throw; that throw is caught and returned as `{ ok:false, error:"invalid share link" }`.

`data-action="copy-link"` in the editor toolbar builds `location.origin + location.pathname + '#edit=' + EncodeLayoutToUrlHash(getLayout())` and writes it to the clipboard via `navigator.clipboard.writeText` (fire-and-forget; a failure is shown as a toast, never thrown). On load, module 10's app-shell is responsible for checking `location.hash` for an `edit=` fragment and, if present, calling `DecodeLayoutFromUrlHash` and passing the result as `AirportEditorOptions.initial` — `airportEditor.ts` itself never reads `location.hash` (kept out of the contract's DOM-global surface; `CreateAirportEditor`'s only input channel is `options.initial`).

### 4.8 PWA

`src/ui/pwa.ts`'s `registerServiceWorker(swUrl)`:
```ts
async function registerServiceWorker(swUrl: string): Promise<ServiceWorkerRegistrationHandle> {
  const updateCbs: Array<() => void> = [];
  if (!('serviceWorker' in navigator)) {
    return { registered: false, scope: undefined, error: 'serviceWorker unsupported', onUpdateAvailable: (cb) => { updateCbs.push(cb); } };
  }
  try {
    const reg = await navigator.serviceWorker.register(swUrl);
    const hadController = !!navigator.serviceWorker.controller;
    reg.addEventListener('updatefound', () => {
      const installing = reg.installing;
      if (!installing) return;
      installing.addEventListener('statechange', () => {
        if (installing.state === 'installed' && hadController) updateCbs.forEach((cb) => cb());
      });
    });
    return { registered: true, scope: reg.scope, error: undefined, onUpdateAvailable: (cb) => { updateCbs.push(cb); } };
  } catch (e) {
    return { registered: false, scope: undefined, error: String(e), onUpdateAvailable: (cb) => { updateCbs.push(cb); } };
  }
}
```
`hadController` distinguishes "first ever install" (no reload prompt needed — nothing to update from) from "an update to an already-controlled page" (prompt to reload). See §5.4–§5.5 for the manifest and service-worker file contents this registers against.

### 5.5 `public/service-worker.js` (exact content)

```js
const CACHE_VERSION = 1;
const CACHE_NAME = `tejas-sim-v${CACHE_VERSION}`;
const PRECACHE_URLS = ['/', '/index.html', '/manifest.webmanifest'];

self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open(CACHE_NAME).then((cache) => cache.addAll(PRECACHE_URLS)).then(() => self.skipWaiting())
  );
});

self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys()
      .then((keys) => Promise.all(keys.filter((k) => k !== CACHE_NAME).map((k) => caches.delete(k))))
      .then(() => self.clients.claim())
  );
});

self.addEventListener('fetch', (event) => {
  const req = event.request;
  if (req.method !== 'GET') return;
  const url = new URL(req.url);
  if (url.origin !== self.location.origin) return;
  event.respondWith(
    caches.match(req).then((cached) => {
      if (cached) return cached;
      return fetch(req)
        .then((res) => {
          if (res.ok) {
            const copy = res.clone();
            caches.open(CACHE_NAME).then((cache) => cache.put(req, copy));
          }
          return res;
        })
        .catch(() => caches.match('/index.html'));
    })
  );
});

self.addEventListener('message', (event) => {
  if (event.data === 'skipWaiting') self.skipWaiting();
});
```
Strategy: cache-first for everything same-origin, with a background write-through cache-on-success for any request not in `PRECACHE_URLS` (this is how Vite's hashed `/assets/*.js`/`*.css` output gets cached — the service worker does not need to know their names ahead of time, only that the first request for each is a normal network fetch that then gets cached for every subsequent load, including offline). `activate` deletes every cache whose name isn't the current `CACHE_NAME`, so bumping `CACHE_VERSION` (module 11's job whenever a breaking static-asset change ships) evicts all stale entries. Cross-origin requests (none exist in this project today — no CDN, no API) are explicitly passed through un-cached (`return` with no `respondWith`) so the strategy stays correct if one is ever added.

## 6. Performance budget

- **Menus (main/mission-select/settings/pause/debrief/loading)**: static DOM, no per-frame work, no `requestAnimationFrame` loop while idle. Construction (`CreateX`) must complete synchronously in under `5` ms for any realistic `MissionSelectOptions.missions.length` (≤ 50).
- **Airport editor redraw**: one `CanvasRenderingContext2D` full-canvas repaint per `pointermove`/pan/zoom event, budget `<= 16` ms on a Medium-tier desktop and `<= 33` ms on a Low-tier mobile device (30 fps floor while dragging), at the maximum layout size (`EDITOR_MAX_RUNWAYS`=8, `EDITOR_MAX_TAXIWAYS`=30 × up to `EDITOR_MAX_TAXIWAY_POINTS_TOTAL`/30=10 pts avg, `EDITOR_MAX_APRONS`=15). Redraw cost is `O(runways + ΣtaxiwayPoints + ΣapronPoints)` — one pass building each feature's screen-space path, no per-feature offscreen canvases/caching required at this scale.
- **`ValidateEditorLayout`**: `O(runways²)` for the overlap check (rule 4; ≤ `8² = 64` `RectanglesOverlap` calls) plus `O(Σpoints)` for everything else; budget `<= 4` ms at max layout size. Called after every committed mutation (§4.5.2), never per `pointermove`.
- **Quality-tier benchmark**: bounded wall-clock `BENCHMARK_DURATION_MS` (2000 ms) plus `< 100` ms of setup/teardown overhead; runs once at first boot (the caller, module 10, decides whether/when to re-run it — `src/ui` has no re-run policy of its own). The benchmark's own VBO is built once (`Float32Array` of `BENCHMARK_TRIANGLE_COUNT * 3 * 5` floats — 2 pos + 3 color per vertex) before the `requestAnimationFrame` loop starts; the loop itself allocates nothing per frame (single `drawArrays` call, no new typed arrays, no new closures — the `tick` callback is a hoisted named function, not `.bind`/arrow-created fresh per frame).
- **Pointer-drag hot path** (`screenToWorld`/handle math, §4.5.2, potentially called at display refresh rate while dragging): reuses two module-level scratch `EditorPoint`-shaped objects rather than allocating a fresh object per `pointermove`, as a *recommendation* (not a hard "zero allocation" requirement — the editor is not one of `00-architecture.md` §2's defined hot paths, which are limited to `src/physics`/`src/ai`/`src/combat`/`src/core`'s step loop/`src/render`+`src/hud`'s frame loop) to avoid visible GC pauses during a drag on low-end mobile.
- **PWA service worker**: `fetch` handler adds no more than one `caches.match` + (on miss) one `fetch` + one `cache.put` per request; no synchronous work in `install`/`activate` beyond the listed `caches.open`/`caches.keys` calls.

## 9. Open assumptions

- **`AirportLayout` schema mismatch risk (module 05).** `contracts/ui.ts` cannot import `contracts/airport.ts` — module 05 is drafted in parallel and its `AirportLayout` shape is unseen, and `00-architecture.md` §9.2 only pins the five-field `AirportFlattenZone` shape (which `EditorFlattenZone` mirrors exactly, field-for-field, by name). Every other editor type (`EditorRunway`, `EditorTaxiway`, `EditorApron`, `EditorAirportLayout`/`...Export`) is this module's own best-effort, self-contained schema, chosen to reuse `core.ts`'s existing naming where it already overlaps (`headingRad`, `lengthM`, `widthM`, `elevationM`, `frequencyMhz`, `glideslopeAngleRad`, matching `RunwayInfo`/`IlsInfo`). Reconciling the exact exported JSON with whatever `contracts/airport.ts`'s parser actually expects is necessarily an integration-time task for module 10 (which imports everything); because `airportEditorExport.ts` is a single small, isolated file, that reconciliation is a localized adapter, not a redesign.
- **Control rebinding bridges to an unseen input contract (module 09).** `BindableAction`/`KeyBinding` are local to `ui.ts` for the same reason. Module 10 must translate `SettingsState.keyBindings` into whatever `contracts/input.ts`'s actual `InputMap` shape requires; `src/ui` never talks to `src/input` directly (disallowed by `00-architecture.md` §10 regardless).
- **No audio subsystem exists anywhere in this project** (no module owns sound; `core.ts` defines no audio-related types or events). Settings therefore has no volume control — this was considered and deliberately excluded, not overlooked.
- **Settings persistence across page reloads is explicitly out of scope for `src/ui`.** No module in this project owns a "user preferences" storage contract. `src/ui/settings.ts` performs zero `localStorage`/IndexedDB I/O; `initial`/`onChange` make module 10 the sole place that could add persistence later without touching this module.
- **The quality-tier benchmark measures a synthetic raw-WebGL triangle-soup scene, not actual game rendering** (module 08's Three.js scene). `src/ui` cannot depend on `src/render` (§10 import rules), so this is the best proxy available; real in-game frame cost will differ somewhat (higher, given terrain/wireframe/HUD overhead) from the benchmark's number. `QualityTier`'s definition already treats this as an estimate, not a guarantee (a later in-game auto-downgrade, if desired, is out of this module's scope).
- **GPU renderer-string token tables (§5.1/§5.2) are a heuristic snapshot, not an authoritative database.** They will age as new GPUs ship and are deliberately small/conservative — an unrecognised string always scores neutral (`0`), never penalised, so the tier is driven primarily by the measured benchmark fps in the common case of an unmatched GPU.
- **`DebriefStats` is computed and supplied by `src/main.ts` (module 10)** from `core.ts`'s `MissionEndedEvent` (which `World` now emits — see `10-core-worker.md` section 4.1b, resolved from an earlier "no module evaluates mission objectives" gap) plus this session's own running kill/shot counters, accumulated client-side from the `gunFire`/`hit`/`kill` `SimEvent` stream over the mission's lifetime (`contracts/ui.ts`'s own `DebriefStats` doc comment gives the exact aggregation source). This contract fixes the *shape* module 10 must populate; the counting logic itself (module 10's `main.ts`) is straightforward accumulation, not something this document needs to re-derive.
- **`tsc --noEmit --strict` for the isolated contracts audit is assumed to include `"lib": ["ES2022","DOM"]`** (verified locally for this file with TypeScript 7.0.2 using exactly that lib set — see §8 item 1). Without `DOM` in `lib`, every `HTMLElement`/`HTMLCanvasElement` reference in this file fails to resolve; since `contracts/render.ts`, `contracts/input.ts` and `contracts/verify.ts`'s HUD/DOM-adjacent surfaces almost certainly need the same lib, this is treated as a safe, shared assumption rather than a gap unique to this module.
- **Mobile orientation/touch heuristics (`matchMedia('(orientation: portrait)')`, `matchMedia('(pointer: coarse)')`, `screen.width`/`height`) are not implemented by `jsdom` by default** and must be mocked by `tests/ui/orientationPrompt.test.ts` (module 12) — flagged here since it is the one place this module's tests require a manual DOM API shim rather than jsdom's built-in behaviour.
- **PWA icon *pixel content* is not specified** — only sizes/format/`purpose` (§5.4) are part of the contract; any opaque PNG of the exact declared dimensions satisfies every mechanically-checkable acceptance criterion. This is treated as a graphic-design asset, not logic, and is the one deliberate content gap in this spec (a flat `#0a0d12`-background placeholder square is sufficient).
- **Optional terrain preview in the editor (`AirportEditorOptions.sampler`)** is specified only at the level of "use it if present, flat grid if absent" (§3's contract comment) with no required sampling resolution pinned in this document, since it is a cosmetic underlay, not something any other module reads back; `src/ui/airportEditor.ts` is free to sample it at a coarse fixed resolution (e.g. one `heightAt` call per ~20 screen-pixels of grid, redrawn only on pan/zoom, not on every drag) without affecting any acceptance criterion above.
